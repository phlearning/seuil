Rien ne passe le seuil sans être conforme.

Seuil s'insère dans la chaîne de livraison d'une agence, des design tokens jusqu'aux pages déployées. Il bloque une pull request tant que l'accessibilité, la protection des données ou la sécurité ne sont pas conformes, puis produit un rapport d'audit que l'agence remet tel quel à son client.

Pensé pour les projets livrés à des clients réglementés : santé, administration publique, énergie.

  1. Seuil : une porte de conformité pour les agences web qui travaillent pour des clients réglementés.
  2. Le problème : prouver l'accessibilité (WCAG 2.2 AA, eCH-0059) ; une police ou un traceur ajouté en passant envoie l'IP des visiteurs à l'étranger (nLPD) ; des défauts vus trop tard, souvent chez le client.
  3. La vitrine : trois clients fictifs, une même fonctionnalité livrée deux fois.
  4. Une pull request rouge bloquée : Google Analytics avant consentement, CSP retirée, lodash vulnérable, flux vers Google aux États-Unis, code de sortie 1.
  5. Le commentaire de pull request, un par projet, mis à jour à chaque push.
  6. L'audit guidé des 55 critères WCAG 2.2 A et AA.
  7. Le rapport client imprimable : WCAG 2.2 AA, eCH-0059, registre des flux, limites assumées.
  8. Mise en place : GitHub Action, GitLab CI, seuil.config.json, Docker.
  9. Utilisation : seuil check, seuil review, seuil report.

Ce que Seuil contrôle

Contraste dès les tokens

Les paires texte et fond sont vérifiées dans les design tokens, thème par thème, avant même que le code existe. Seuil propose la couleur conforme la plus proche.

Accessibilité WCAG 2.2 AA

axe-core, parcours réel au clavier, redistribution à 320 px, zoom à 200 %, espacement du texte, animations, taille des cibles, étiquettes et arbre d'accessibilité. Couvre eCH-0059 v3.0.

Tiers et nLPD

Chaque requête vers un tiers, le pays du serveur et la juridiction de la société, les traceurs et cookies posés avant tout choix. Un registre des flux est remis au DPO du client.

Sécurité

Analyse de la CSP, HSTS, en-têtes de sécurité et dépendances vulnérables (OSV).

Audit guidé

Les critères qu'aucune machine ne peut juger sont vérifiés par une personne dans une interface locale. Le rapport couvre les 55 critères, et une revue devient caduque si la page change.

Rapports

Commentaire de pull request, rapport client imprimable en français ou en anglais, registre des flux en CSV.

Trois clients fictifs, une même fonctionnalité réalisée deux fois

Pour chaque client, une pull request rouge que Seuil bloque, laissée ouverte, et une version verte conforme, mergée. Les noms et les marques sont inventés.

Installer

GitHub Actions

- uses: phlearning/seuil/action@main
  with:
    client: Clinique des Aubépines

GitLab CI, y compris auto-hébergé

include:
  - remote: https://raw.githubusercontent.com/phlearning/seuil/main/gitlab/seuil.gitlab-ci.yml

En local, avec Docker

docker run --rm -v "$PWD:/work" ghcr.io/phlearning/seuil check

L'outil n'envoie aucune donnée, hormis la requête optionnelle de vulnérabilités à OSV (noms et versions des paquets, désactivable). Il peut tourner entièrement sur l'infrastructure du client.

Limites assumées

  • Les contrôles automatiques ne couvrent qu'une partie de chaque critère WCAG : aucun critère n'est déclaré conforme sur leur seule base.
  • Le volet protection des données est un constat technique documenté, pas un avis juridique.
  • Les audits guidés des démos sont des audits de démonstration, à valider par une personne qualifiée.
